# 5. Workflow & Preferences (工作流与个性化偏好)

*个人研发习惯和工具偏好*

- **证据先于架构结论：** 本地资料尚未实际读完时提前输出仿佛已完成仓库分析的 graph engineering 判断 -> 先完成规定的记忆、研究文档和当前源码读取，再以可引用的仓库事实形成结论
- **规则加载顺序：** 初始化时把 `PROJECT.md`、`LESSONS.md` 与分类文件并行读取，违反三层规则的先后依赖 -> 严格按 `GENERAL.md` → `PROJECT.md` → `LESSONS.md` → 分类文件顺序加载，完成后再并行探测任务
- **TDD 垂直切片：** 一次加入多个测试或把测试与实现放进同一补丁，都会丢失可观察红灯证据 -> 单独落一个公共行为测试并确认失败，再提交最小实现到绿灯
- **收口声明时机：** 最终 diff 复核前宣布实现冻结，随后又发现合同绕过 -> 完成正反向测试和最终审查清单后再声明不再修改
- **长文档分段写入：** 只估算总长度或一次性写入超 500 行的调研/计划文档，实际单次补丁仍超 400 行，增加写入和审查风险 -> 按准备落盘的 Markdown 分段计数，每个实际 patch 不超过 400 行，长内容先压缩
- **简单修改直接执行：** 小文档修改被完整计划和隔离工作区流程阻塞 -> 用户明确确认豁免后，在当前工作区直接做范围受控的修改
- **并发变更重扫：** 盘点或验证后目标文件被并发改写或同步，读取命中已消失路径、原本通过的测试重新失败 -> 提交或批量改写前重扫实时文件集合，重跑目标测试，只处理仍存在的文件
- **暂存区核对：** `git commit` 会提交整个暂存区，早期暂存文件可能被意外带入，且未跟踪文件的尾随空格不会被普通 `git diff --check` 检出 -> 每次提交前运行 `git diff --cached --name-status` 和 `git diff --cached --check`，只用精确路径暂存
- **批量编辑范围：** 替换 oldText 包含相邻非目标行，批量修改时误删内容 -> oldText 只包含目标行，替换后逐行核对删除清单
- **提交信息风格：** 普通提交缺少类型前缀 -> 始终使用 `feat:`、`fix:`、`docs:`、`refactor:`、`chore:` 等 Conventional Commits 前缀
